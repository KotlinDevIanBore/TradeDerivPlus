# AUTO mode — deferred items

Anything consciously put off during the AUTO-mode phases, with where it came from and where it is
meant to land. The point is that a promise made in one checkpoint's report does not depend on someone
rereading every prior report to notice it was made.

**Append when you defer something. Move it to Closed when it lands, with the checkpoint that did it.**

| Whether Safaricom deduplicates a repeated `OriginatorConversationID` | B2C CP1 | Needs sandbox credentials + a callback catcher | **This gates one optimisation, not the design.** `scripts/daraja_b2c_probe.py` answers it: send a payout, send the identical request again, see whether Daraja refuses the duplicate. The production system next door reached the same rule independently, under real stakes: it logs an ambiguous send, alerts an operator, and neither refunds nor resends. |

| Withdrawals are off, and turning them on is a SQL update | B2C CP0 | B2C CP4 | `withdrawals_enabled` is seeded FALSE and there is no console control for it, deliberately: the only correct time to turn it on is when the payout exists, which is what CP4 does. | `WithdrawnTodayUSD`'s pending clause is unreachable through `Withdraw` | B2C CP0 | Accepted | The cap counts pending alongside completed, but the one-in-flight index means an account can only ever have one pending withdrawal — so the clause only changes an answer in the window where the cap is checked and the insert has not yet been refused. | Resolve's audit row is written after the settlement, not with it | STK CP4 | Accepted | The credit belongs to `settleDeposit`'s transaction, whose T→W lock order every settlement keeps, and the console's audit must not be the first path to take the wallet lock from outside it. Recorded so nobody "fixes" it by wrapping both in one transaction. |
