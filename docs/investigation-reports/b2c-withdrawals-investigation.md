# Investigation: B2C withdrawals via Daraja

**Date:** 25 September 2026 · **Branch:** `digit-contracts-enabled-by-default`
**Kind:** read-only survey. No code was changed and no credential was added.
**Basis:** the codebase; Safaricom's own SDK repositories (first-party); a mirror of the Daraja
portal's documentation text (first-party text, third-party hosting); community sources, marked as
such. The evidence discipline is the STK query investigation's: three tiers, kept apart.

---

## 0. Summary

- **B2C is a different API from STK push in every dimension that matters**: a different
  credential mechanism (an RSA-encrypted initiator password, not the base64 passkey), a different
  actor (an "API user" created on the M-PESA org portal, with a role), a second callback URL, a
  differently shaped result payload, and a result-code vocabulary that **reuses STK's numbers with
  different meanings**. The only things that carry over from `pkg/mpesaclient` are the OAuth token
  cache, the base URL, the HTTP plumbing and the `errorCode` envelope.
- **Withdrawal is the first "money left our side, now we wait on Safaricom" case in the codebase.**
  Deposits are the mirror image, and the deposit machinery (`mpesa_requests`, `settle()`, the
  reconciler) is deposit-shaped by name and by column. It is a pattern to copy, not a table to
  reuse.
- **The hazards are the double-credit hazard inverted, and worse.** A retried B2C call is cash
  leaving the business twice; a failed one is a customer debited with no payout and — today — no
  path back. There is no idempotency protection on `POST /wallet/withdraw` at all. B2C v3's
  `OriginatorConversationID` is Safaricom's own answer to double disbursement and should be the
  spine of the design.
- **B2C has a status query, but it is asynchronous** (the answer arrives at a callback URL), so a
  reconciler for payouts is not CP3's pass with a different table; it is a request-then-wait.
- **What cannot be known from documentation**: whether B2C is enabled on the account, which
  certificate to use, the initiator's role, float. All of it is a conversation with Safaricom.

§1–§4 follow the brief's headings. §5 is the recommended shape, not the plan.

## 1. What Daraja's B2C API requires

### 1.1 The request — confirmed first-party

Safaricom's own SDKs send the same ten fields. `safaricom/mpesa-node-library`
`src/endpoints/b2c.js` posts to **`/mpesa/b2c/v1/paymentrequest`** with:

| Field | What it is | Have it today? |
|---|---|---|
| `InitiatorName` | username of the **API user created on the M-PESA org portal** | **No** — no such concept in config |
| `SecurityCredential` | that user's password, **RSA-encrypted with Safaricom's public certificate, base64** | **No** — and it is not the STK password (§1.2) |
| `CommandID` | `BusinessPayment` (SDK default), `SalaryPayment`, `PromotionPayment` | n/a |
| `Amount` | KES, whole number | yes (`Ceil().IntPart()` pattern from `InitiateSTK`) |
| `PartyA` | the **B2C** shortcode the money leaves | **Maybe** — `MpesaShortcode` is the paybill/till used for deposits; whether it can disburse is §4 |
| `PartyB` | customer MSISDN, `2547…` | yes (`mpesaclient.NormalizePhone`) |
| `Remarks`, `Occasion` | free text, 2–100 / 1–100 chars | n/a |
| `QueueTimeOutURL` | **second callback URL**, hit if the request times out in Safaricom's queue | **No** — one `MpesaCallbackURL` exists |
| `ResultURL` | where the outcome is posted | **No** — the existing URL is STK-shaped (§1.4) |

`safaricom/mpesa-api-C-Sharp` `B2CApi.cs` sends the identical body and leaves
`SecurityCredential` as a literal placeholder — Safaricom's own C# sample does not show how to
produce it.

**v3.** The documentation mirror (§1.6) gives the endpoint as
**`/mpesa/b2c/v3/paymentrequest`** with one additional field:

> `OriginatorConversationID` — "Unique string generated by the merchant system for every B2C
> request to avoid double disbursement"

A community SDK (`kepas-tech/daraja-js` PR #43) routes to v3 when the caller supplies that id and
to v1 otherwise, and uses the same id to query status for "a transaction that never returned a
receipt". This is the single most important fact in this section for §3: **Safaricom offers a
caller-chosen idempotency key on payouts.** Safaricom's own SDKs predate it and send v1. Which
version the sandbox and the production account accept is not confirmable from documentation.

### 1.2 The security credential — a different mechanism, confirmed first-party

STK push's `Password` is `base64(shortcode + passkey + timestamp)`
(`pkg/mpesaclient/client.go:147-148`). B2C's `SecurityCredential` is not that, and nothing in
the existing client produces it. Safaricom's node library, `src/helpers/security.js`:

- `crypto.publicEncrypt({ key: <certificate file>, padding: crypto.constants.RSA_PKCS1_PADDING })`
- the certificate is read from a file path (`certPath`), PEM as-is
- output `.toString('base64')`

So: **RSA PKCS#1 v1.5 encryption of the initiator's plaintext password under Safaricom's public
certificate, base64-encoded.** Not OAEP. The library bundles the sandbox certificate at
**`keys/sandbox-cert.cer`**; production uses a different certificate (every source agrees;
where to obtain it is §4). In Go this is `x509.ParseCertificate` + `rsa.EncryptPKCS1v15` +
`base64.StdEncoding` — standard library, about fifteen lines, but it needs the certificate on
disk or in config and an **initiator password in config**, which is a new secret with the same
handling rules as the consumer secret.

The mirror adds one operational note: the initiator password "should be limited to specific
special characters such as #, &, %, and $"; parentheses and `@` are problematic. Result code
`8006` is "security credential locked" — a wrong password locks the API user, which is a support
call, not a retry.

### 1.3 Credentials and configuration beyond what deposits use

| Needed | Exists | Notes |
|---|---|---|
| Consumer key/secret, OAuth token | **yes** — `accessToken`, `client.go:100-138` | same token serves B2C (same `oauth.js` in Safaricom's SDK) |
| Base URL | yes — `MpesaBaseURL` | |
| Initiator name | **no** | an API user created on the M-PESA **organisation** portal, not the developer portal |
| Initiator password | **no** | new secret; encrypted per §1.2 on every request |
| Safaricom public certificate (sandbox / production) | **no** | file or env; the two differ |
| B2C-capable shortcode | **unknown** | §4 |
| `ResultURL` | no | new route, B2C-shaped |
| `QueueTimeOutURL` | no | new route; may be the same handler |

### 1.4 The callback — distinct from STK's, in shape and in vocabulary

**Shape.** STK's callback (`client.go:72-87`) is `Body.stkCallback{MerchantRequestID,
CheckoutRequestID, ResultCode, ResultDesc, CallbackMetadata.Item[]{Name, Value}}`. B2C's result is
a different document. The mirror's field list and a captured production payload (community, gist
`TralahM/e2bf…`, 2019) agree:

```json
{ "Result": {
    "ResultType": 0, "ResultCode": 0, "ResultDesc": "The service request is processed successfully.",
    "OriginatorConversationID": "11369-5305957-1",
    "ConversationID": "AG_20190103_00004ad7c21029e28510",
    "TransactionID": "NA30XPKKVCW",
    "ResultParameters": { "ResultParameter": [
      { "Key": "TransactionAmount", "Value": 100 },
      { "Key": "TransactionReceipt", "Value": "NA30XKHVCW" },
      { "Key": "ReceiverPartyPublicName", "Value": "2547XXXXXXX - JOHN DOE" },
      { "Key": "TransactionCompletedDateTime", "Value": "03.01.2019 17:48:32" },
      { "Key": "B2CUtilityAccountAvailableFunds", "Value": 4425.00 },
      { "Key": "B2CWorkingAccountAvailableFunds", "Value": 0.00 },
      { "Key": "B2CRecipientIsRegisteredCustomer", "Value": "Y" },
      { "Key": "B2CChargesPaidAccountAvailableFunds", "Value": 0.00 } ] },
    "ReferenceData": { "ReferenceItem": { "Key": "QueueTimeoutURL", "Value": "…" } } } }
```

Points that matter for the code:

- **Top-level key is `Result`, not `Body`.** `mpesaclient.Callback` cannot decode it; the
  existing `POST /api/v1/mpesa/callback` handler (`wallet_handler.go:145-157`) binds
  `mpesaclient.Callback` and would see an empty `CheckoutRequestID`. A B2C result must have its
  own route or its own decoder — it cannot share the STK handler.
- **Three identifiers, none of them a `CheckoutRequestID`.** `OriginatorConversationID` (ours,
  under v3; Safaricom's under v1), `ConversationID` (Safaricom's, returned synchronously), and
  `TransactionID` (the M-Pesa receipt, only on success). Correlation back to our withdrawal row has
  to be by `OriginatorConversationID` or `ConversationID`, both known before the callback arrives.
- **`ResultParameter` is `Key`/`Value`, not `Name`/`Value`.** `Callback.ReceiptNumber()` does not
  apply; the receipt is `TransactionReceipt` (and duplicated as `TransactionID`).
- **The payload carries the business's remaining float** (`B2CUtilityAccountAvailableFunds`).
  That is an observability gift: every successful payout reports how much is left to pay the next
  one.
- **Two URLs.** `QueueTimeOutURL` receives a notification when the request timed out in
  Safaricom's queue — which is *not* "the payout failed"; it is "we do not know". The STK path has
  no equivalent. Treating a timeout notification as a failure is the payout analogue of the
  denylist mistake the STK investigation refused.

**Vocabulary — the same numbers mean different things.** The mirror's B2C result-code table
(first-party text, unverified against the portal):

| Code | B2C meaning | STK meaning of the same number (`humanResult`, `TerminalFailureCodes`) |
|---|---|---|
| 0 | success | success |
| **1** | **the business's utility account has insufficient funds** | the *customer's* M-Pesa balance is insufficient |
| 2 / 3 / 4 / 8 | limit rules: below minimum / above per-transaction max / daily limit / recipient's balance would exceed max | — |
| 11, 2006 | B2C account inactive | — |
| 21 | initiator lacks the B2C role | — |
| **2001** | **initiator name or encrypted password wrong** | the customer entered a wrong PIN |
| 2028 | shortcode not permitted for B2C ("product assignment") | — |
| 2040 | recipient not registered on M-Pesa | — |
| 8006 | API user's password locked | — |
| `SFC_IC0003` | recipient number does not exist | — |

`pkg/mpesaclient.TerminalFailureCodes` (`{1, 1001, 1032, 1037, 2001}`) and `humanResult`
(`internal/service/mpesa_service.go`) are **STK vocabularies and must not be reused for B2C**:
under them a B2C `1` would be told to the customer as "your balance was too low" when it means
*ours* was, and a `2001` as "wrong PIN" when it means our credentials are wrong. B2C needs its own
allowlist and its own copy. Note also that several B2C failures are **ours, not the customer's**
(1, 11, 21, 2001, 2006, 2028, 8006): the customer did nothing wrong and the copy has to say so.

### 1.5 Status query — exists, but asynchronous

B2C has a status capability, and it is not STK query's. Safaricom's node library
`src/endpoints/transaction-status.js` posts to **`/mpesa/transactionstatus/v1/query`** with
`Initiator`, `SecurityCredential`, `CommandID: "TransactionStatusQuery"`, `TransactionID`,
`PartyA`, `IdentifierType`, `ResultURL`, `QueueTimeOutURL`, `Remarks`, `Occasion`. Two things
follow:

1. **It needs the initiator credential** — the same RSA mechanism as B2C. It cannot be built on
   the STK passkey. (The mirror's "Initiator name and security credential (for B2C and Transaction
   Status APIs)" — quoted by the mctaba production checklist as what arrives with production
   approval — says the same.)
2. **The answer is asynchronous.** The synchronous response is an acknowledgement
   (`ResponseCode "0"`, `ConversationID`); the actual status arrives later at `ResultURL` with
   `ResultParameters` including `ReceiptNo`, `TransactionStatus` (Completed / Pending / Cancelled /
   Declined per the mirror), `Amount`, `FinalisedTime`, `DebitPartyName`, `CreditPartyName`. STK
   query answers in the HTTP response; this does not.

So the STK reconciler's shape — list, query, classify, settle in one pass — does not transplant.
A payout reconciler issues a status request and then has nothing to do until a callback arrives;
the classification lives in the callback handler, not in the pass. The mirror's Transaction
Status doc takes **`OriginalConversationID`** as an alternative to `TransactionID`, and
`daraja-js` PR #43 implements exactly that: a payout that never produced a receipt can still be
asked about by the id we chose. That closes the loop with §1.1's v3.

Two neighbours worth knowing about, same credential, same async shape, from the same SDK:
**Account Balance** (`/mpesa/accountbalance/v1/query`, `CommandID: "AccountBalance"`), whose
result is a pipe-delimited string of the Working, Utility and Charges Paid account balances — the
float check before paying out; and **Reversal** (`/mpesa/reversal/v1/request`), which the mirror
says is for C2B: **"B2C reversals are done manually on the M-PESA portal."** A payout made twice
cannot be undone by API.

### 1.6 What is confirmed, and what is not

**Confirmed, first-party (Safaricom's own repositories):** the v1 endpoint and its ten fields;
the security-credential algorithm (RSA PKCS#1 v1.5, certificate file, base64) and the bundled
sandbox certificate path; the Transaction Status and Account Balance endpoints and fields; that
the same OAuth token is used.

**First-party text, third-party hosting, unverifiable against the source:** everything from the
"documentation mirror" — `JacksCodeVault/mpesa-daraja-mcp`, `daraja_docs_v3/docs/*.md`, a copy
of the Daraja portal's pages. The portal itself (`developer.safaricom.co.ke/APIs/BusinessToCustomer`)
returned 404 to a fetch, as its STK query page did in the earlier investigation. The mirror's
text is internally consistent with the SDKs and with the captured callback, which is the most
that can be said. **Treat its result-code table, parameter descriptions and the v3 endpoint as
"probably right, confirm in sandbox."**

**Community only:** the captured 2019 callback (consistent with the mirror); the v3-routing SDK;
every go-live claim in §4.

**A useful aside for the STK work already shipped.** The mirror's `MpesaExpressQuery.md` — the
page the STK query investigation could not read — shows the query response with
`"ResultCode":"0"` **as a JSON string** while describing the field as "Numeric". CP1's decision to
decode `ResultCode` through `flexInt`, accepting either, was the right guess; this is the first
text of Safaricom's own that shows the string form.

## 2. How this hooks into the existing withdrawal path

### 2.1 What `Withdraw` does today — traced

`WalletService.Withdraw`, `internal/service/wallet_service.go:336-420`. In order:

1. **Gates, outside any lock:** ownership (`:337`); real account only (`:341`, `ErrDemoNotAllowed`);
   **KYC verified** (`:345-351`, `ErrKYCRequired`); amount `> 0` (`:353`) — **there is no minimum
   and no maximum**; `config.go` has `MinDepositKES`/`MaxDepositKES` and nothing for withdrawals;
   phone normalised and validated (`:356-359`).
2. **One transaction (`:363-408`), wallets lock first:** `Wallets.GetForUpdate` (`:364`) →
   `Accounts.GetForUpdate` and the freeze check (`:370-376`) → real balance sufficient (`:379`) →
   `Transactions.Insert` of the withdrawal row (`:383-397`) → `Wallets.Adjust(-amount)` (`:399`).
3. **After commit:** two socket events, `transaction {status: pending, type: withdrawal}` and
   `wallet` (`:413-418`); returns the row; the handler answers **202** with the raw
   `models.Transaction` (`internal/handlers/wallet_handler.go:93`).

The ledger row (`:383-394`): `type withdrawal`, `balance_type real`, **amount negative**, `status
pending`, `reference NULL`, metadata `{amount_kes, phone: "***678", channel: "mpesa"}`.

**Nothing ever moves that row off `pending`.** Every status-mutating call in the codebase is in
the deposit flow (`wallet_service.go:200, 210, 246, 286`); `Transactions.Insert`'s own comment
says the ledger is updated only for the deposit transition (`transaction_repo.go:17-18`);
`AdminService.ResolveDeposit` refuses non-deposits by name (`admin_service.go:296-298`). No test
asserts a withdrawal completes, `smoke.py`'s only withdrawal check asserts the KYC refusal
(`scripts/smoke.py:263-267`), and there is no withdrawal e2e spec.

**The exposure today is smaller than it reads.** The path is reachable only by a KYC-verified user,
KYC is approved only by an admin from the console, and the user-facing verification flow does not
exist — the sheet's own dead end says *"Verification is not available yet."*
(`web/src/features/wallet/WithdrawSheet.tsx:89`). So no real customer can currently reach a
withdrawal that pays nobody. That is a mitigating fact, not a design; it is one console click
from untrue.

### 2.2 Two structural facts that constrain where B2C goes

**The full phone number is discarded.** `Withdraw` validates and normalises the MSISDN and then
persists only `maskPhone(phone)` (`:391`, → `"***678"`). After the transaction commits, the
destination number exists nowhere. A B2C request made after commit — the natural place, §2.3 —
has the number only because it is still in the request's memory; a crash-recovery resend or an
operator's retry has no number to send to. The deposit side already keeps the full
`phone_number` on `mpesa_requests` (`migrations/0001_init.up.sql:53`), so the precedent for
persisting it on a payout row exists.

**`Withdraw` takes the wallet lock first.** `settleDeposit` is transactions-row → wallets-row
(`:273-299`); `Withdraw` is wallets-row → `INSERT` (`:364`, `:395`). The plan for the STK work
recorded why that is legal: every wallet-first writer only *inserts* ledger rows, never locks an
existing one, so there is no cycle — and forbade any new path that takes the wallet lock before
`UpdateStatusIfPending` (`stk-reconciliation-plan.md:136-142`). A payout **result** handler
flips an existing row and moves money. **It must be written in `settleDeposit`'s order**, guarded
`UpdateStatusIfPending` first, `Wallets.Adjust` second, in one `WithTx` — not in `Withdraw`'s,
which is the order a developer copying the nearest code would reach for. Getting this wrong is
the first W→T path in the codebase and a deadlock against every deposit settlement.

### 2.3 Where the B2C call goes — before, after, inside, or apart

Four placements, three of them wrong:

| Placement | What goes wrong |
|---|---|
| **Before the debit** | pays out before funds are reserved; a concurrent second withdrawal can overdraw — the exact thing `Withdraw`'s comment says the up-front debit exists to prevent (`:333-335`) |
| **Inside the transaction**, after the debit, before commit | a network call under two row locks; and if B2C accepts and the commit then fails, Safaricom has paid and the ledger says nothing happened — the worst state available |
| **A separate pass only** (reconciler-style, no call in the request) | works, but turns every withdrawal into a minutes-late payout and makes the reconciler a money-*sender* rather than a checker; the pass should be for the ambiguous cases, not the happy path |
| **After commit, in the same request** | the deposit path's own shape — row first, Daraja second, stamp third (`Deposit`, `wallet_service.go:160-215`) |

The fourth is right, and it is what `Deposit` already does: insert the pending row (`:192`),
call `InitiateSTK` (`:197`), then write the id back with `MergeMetadata` (`:210`) — the method
that CP0 introduced precisely because the stamp-back write used to re-assert `pending` and
revert a settlement that had landed in the gap. The same three phases, for a payout:

1. **Reserve** — `Withdraw`'s transaction as it is, plus a payout row (§2.5) carrying **our own
   `OriginatorConversationID`, generated before the call, unique, and the full MSISDN**.
2. **Request** — B2C v3 with that id, outside any lock.
3. **Record** — on synchronous acceptance (`ResponseCode "0"`), stamp `ConversationID` on the
   payout row with a metadata-only write; on a synchronous **rejection** (an `errorCode`
   envelope or a non-zero `ResponseCode`), no money moved — refund through the settle path
   (§2.4) with source `rejected`; on a **transport failure or timeout**, leave the row as it is —
   Safaricom may or may not have received it — and let the reconciler ask (§3.2).

The gap between phase 1's commit and phase 2's send is where the process can die. Under v3 the
row already holds the one id that lets us ask Safaricom "did you ever get this?" and — if the
mirror's description is right — resend without paying twice. Under v1 the same gap is
unrecoverable by API: nothing identifies our request until Safaricom's `ConversationID` comes
back, and a resend is a second payout. **v3's `OriginatorConversationID` is therefore not a
nicety; it is the difference between a recoverable design and one that needs an operator to
check the M-PESA portal after every crash.** Whether the sandbox and the production account
honour v3, and whether Safaricom actually dedupes on the id, is the first thing a probe must
establish (§5).

### 2.4 The equivalent hazard, and the guards that carry over

Deposits had one race: two deliveries of "paid" crediting twice. Payouts have three, and they
point the other way.

| # | Race | Deposit analogue | What guards it |
|---|---|---|---|
| P1 | **two B2C requests for one withdrawal** — a retry after an ambiguous send, a double-submitted request, a crash-and-resend | none; Daraja never sent two pushes for one call | *ours to build*: exactly one request per payout row, enforced by a guarded "mark requested" write before the call (`WHERE requested_at IS NULL`), plus v3's id if Safaricom dedupes. Nothing in `mpesa_requests`, `settle` or `UpdateResult` helps here — they guard outcomes, not requests |
| P2 | **two refunds** — the Result and the QueueTimeOut both arriving, or Daraja retrying a failure result | two callbacks crediting twice | `UpdateStatusIfPending` (`transaction_repo.go:37-46`) — type-agnostic, works on a withdrawal row unchanged, the same guard-in-the-UPDATE; refund only when `won` |
| P3 | **refund, then "paid"** — a timeout notification treated as a failure, the wallet refunded, and then the Result says the customer was paid | "failed, then succeeded" — the class D2 removed by never writing Failed from a query | the same rule inverted: **never refund on the strength of a timeout or an unresolved status; refund only on Safaricom's explicit terminal failure.** A timeout is "we do not know", and money must not move on "we do not know" |

P3 is the payout version of the STK investigation's central decision, and the consequence of
getting it wrong is worse: a wrong deposit credit is the house's money and clawable; a refund
followed by a real payout is cash gone to a customer who now holds both, and the mirror's own
Reversal document says **B2C reversals are done manually on the M-PESA portal** — there is no
API to take it back.

**What carries over from the deposit machinery, and what does not.** The *pattern* is exactly
right and should be copied: one `settle`-shaped function as the only writer of an outcome
(`mpesa_service.go:368-380`); the outcome guard inside the UPDATE; an `OnResult` seam so the
Daraja-speaking service never touches wallets (`wallet_service.go:38`); the
`Start`/`tick`/`TryLock` reconciliation skeleton (`:184-235`). The *code* is deposit-shaped in
every concrete piece: `DepositResult`, `settle`/`settleAs`/`HandleCallback`/`ResolveByAdmin` all
keyed on `checkoutID`; `success := resultCode == 0` against a `Body.stkCallback` payload;
`mpesaclient.Callback` and `ReceiptNumber()`; `humanResult` and `TerminalFailureCodes` (STK
vocabularies, §1.4); `simulateCallback`; the `Reconcile*` labels. A payout needs a **sibling**,
not a parameter: `MpesaPayoutService` with its own result type, its own settle keyed on the
payout's ids, its own callback routes, registering `settlePayout` beside `settleDeposit`.

### 2.5 Is there an existing "money left, awaiting confirmation" pattern?

**No. Withdrawal is the first external-counterparty case.** The nearest things:

- `balanceAffectingRows` (`internal/repository/reconciliation.go:10-30`) already *names* the
  state: *"A pending WITHDRAWAL has moved money… A pending withdrawal must count."* The ledger
  arithmetic for "debited, awaiting payout" exists and is tested
  (`wallet_integration_test.go:177-180`). What does not exist is anything that resolves it.
- Digit contracts debit the stake at open and settle later (`DigitService.Open`, then the tick
  settler) — money leaves the wallet and a later event decides the outcome. But the later event
  is *ours* (a price tick); nothing waits on a third party.
- `mpesa_requests` is the inverse: money arrives to us, we credit. **It cannot be reused** for
  payouts, and not for want of columns: the reconciler's `ListPending` selects every pending row
  (`mpesa_repo.go`), hands each to `reconcileOne`, which calls `STKQuery` on it and, on
  `Succeeded`, calls `settle` → `onResult` → **`settleDeposit`**, which credits the wallet
  (`wallet_service.go:286-293`). A payout row in that table would be STK-queried and, if the
  answer parsed as success, would *credit the customer's wallet for their withdrawal*. There is
  no `kind` column and the STK vocabulary (`checkout_request_id`, the search clause, the
  customer-facing copy) is baked into every reader. A separate `mpesa_payouts` table — or a
  `kind` discriminator with a filtered `ListPending` and its own partial index — is the only
  safe option, and 0007's own header argument (state lives beside the request, not on the
  ledger) points the same way.

## 3. Failure modes specific to payouts

### 3.1 Safaricom refuses outright — reverse the debit, but decide what "reverse" means first

Most B2C failures are ours, not the customer's: insufficient float (`1`), inactive B2C account
(`11`, `2006`), initiator without the role (`21`), wrong credentials (`2001`), locked API user
(`8006`), shortcode not permitted (`2028`). Two are the customer's: unregistered recipient
(`2040`) and a non-existent number (`SFC_IC0003`). Four are limits (`2`, `3`, `4`, `8`). **In
every one of these, no money moved**, and the customer's balance should come back automatically
— there is no argument for leaving a customer debited because our float ran out.

But the codebase has two incompatible descriptions of how a refund works, and neither is
implemented:

- `balanceAffectingRows`' comment: *"a failed withdrawal is refunded by a compensating row
  rather than by deleting this one"* (`reconciliation.go:25-26`).
- The predicate itself: a `failed` row **does not count** (`:27-30`). So flipping a withdrawal
  `pending → failed` *adds the amount back to the ledger total by itself*.

Put them together and the arithmetic breaks: flip to `failed` (+amount to the ledger) **and**
insert a compensating credit row (+amount again) against a wallet credited once → drift, the
alarm `ledger_drift_accounts` exists to raise. The consistent options are:

| Option | Ledger | Wallet | Consistent? | Audit trail |
|---|---|---|---|---|
| A. `UpdateStatusIfPending(failed)` + `Wallets.Adjust(+amount)`, **no** compensating row | +amount (row stops counting) | +amount | **yes** | the withdrawal row's metadata (`refunded_at`, result code, source) — the same place a failed deposit keeps its reason |
| B. leave `pending`, insert compensating credit | +amount (new row) | +amount | yes — but the withdrawal is pending for ever, and a late Result can act on it again | two rows, no link between them (this is exactly `Adjust`'s trap, §3.4) |
| C. flip to `failed` **and** compensating row | +2×amount | +amount | **no — drift** | — |

**A is the recommendation**, done in `settleDeposit`'s shape and order — one `WithTx`, the
guarded flip first, the wallet credit second, refund only when `won` — and the predicate's
comment corrected to match. Note the inversion: `settleDeposit`'s *failure* branch touches no
wallet, and a payout's failure branch *must*. It is a credit into a real balance on the strength
of a Daraja message, and deserves the same test standard as the deposit credit: a concurrency
test with several failure deliveries, `assertReconciled` after, and a mutation that removes the
guard. **No test today calls `assertReconciled` after any withdrawal outcome but the pending
one** (`wallet_integration_test.go:180`).

Two refinements. The customer-facing reason must come from a **B2C** copy table, not
`humanResult` — under `humanResult`, code `1` reads "your M-Pesa balance was too low", which
for a payout is false and insulting. And a refund caused by *our* failure (float, credentials,
account state) should page someone: the refund makes the customer whole, but the next
withdrawal will fail the same way.

### 3.2 The ambiguous result — the STK problem inverted, and asynchronous

Three ways to not know: the B2C request's HTTP call fails or times out after send (did Safaricom
get it?); the request is accepted and no Result ever arrives; the `QueueTimeOutURL` is hit
(Safaricom's queue gave up — the mirror's description is "notification if the payment request
times out", which is not "the payment failed").

The rule from §2.4 P3: **money does not move on "we do not know."** The row stays `pending`,
which is already the state `balanceAffectingRows` treats correctly, and the customer's screen
says so. Then ask. Two differences from the deposit reconciler:

1. **The ask is asynchronous.** `Transaction Status` acknowledges and later posts to
   `ResultURL`. So the payout pass is *issue a status request, record that it was issued, back
   off* — and the classification happens in the status-result handler when the answer lands:
   `TransactionStatus: Completed` → mark the withdrawal completed with the receipt; `Declined` /
   `Cancelled` → refund through §3.1; `Pending` → advance the backoff. The CP3 pass's
   `switch out.Status` moves from the pass into a callback.
2. **The key is ours.** Under v3 the status request is by `OriginatorConversationID` (the mirror's
   `OriginalConversationID`; `daraja-js` PR #43's "a transaction that never returned a receipt
   can still be queried"). Under v1 the only handle is Safaricom's `ConversationID`, which we do
   not have if the send itself was the ambiguity. This is §2.3's point again from the other side.

The timeout notification has no STK analogue and needs one explicit decision: it should be
treated as an `Unresolved` *event* — count it, log it, schedule a status request — never as a
terminal outcome. The mutation to run against that decision is "treat a timeout as failed":
the test that must fail is the one where a Result saying paid arrives after the timeout.

Give-up after a horizon, as with deposits, hands the row to an operator with two actions:
**Mark paid** (status completed, no money moves — Safaricom paid, our ledger said so already)
and **Mark not paid** (the §3.1 refund). Both through the payout's settle, both audited, both
guarded — CP4's `ResolveDeposit` is the template, including its "settles the original row so a
late result credits nothing" property, and its refusal to be written as a wallet-first
transaction.

### 3.3 Idempotency — none exists, and the stakes invert

The trace found no idempotency anywhere on the money endpoints: no key field or header on
`withdrawRequest` (`wallet_handler.go:59-63`); no in-flight check in the service; an
unconditional `INSERT` (`transaction_repo.go:19-27`); **no unique index of any kind on
`transactions`** (`0001_init.up.sql:98-99`, `0003_admin.up.sql:50-51`, all non-unique); the
`money` limiter at five immediate requests then one per two seconds per user, per process
(`routes.go:98`, `ratelimit.go:35-38`). The deferred list tracks the deposit key
(`auto-bot-deferred.md:32`) and has no withdrawal row.

Today the missing key is nearly harmless on withdrawal: a double-tap makes two debits that pay
nobody, bounded by the balance check and `Wallets.Adjust`'s non-negative guard
(`wallet_repo.go:49-67`). **The moment a B2C call exists, a double-tap is two real payouts**, and
unlike a double deposit credit it is the business's cash and not recoverable by API. Three
layers, cheapest and strongest first:

| Layer | Mechanism | Cost | What it stops |
|---|---|---|---|
| **One in-flight withdrawal per account** | partial unique index on `transactions (account_id) WHERE type = 'withdrawal' AND status = 'pending'`; `Withdraw` maps the conflict to a clear error ("a withdrawal is already on its way") | one migration line, one error | every double-tap, every retry storm, every two-tab race, *before* any Daraja call — and it is the rule a customer would expect anyway |
| **Our request id** | `OriginatorConversationID` generated and persisted with the payout row *before* the send; sent under v3; the "mark requested" write guarded on `WHERE requested_at IS NULL` | part of the payout table | a second send for one row from our side; if Safaricom dedupes on the id (unconfirmed), a second send from a crash-resend too |
| **Client idempotency key** | `Idempotency-Key` header on `POST /wallet/withdraw` and `/wallet/deposit`, stored with the row | the deferred ticket, shared with deposits | a retried *request* creating a second row — but the first layer already makes a second pending withdrawal impossible, so this becomes a nicety for payouts specifically |

The first layer is the one to insist on. It is enforceable by the database, it needs no
cooperation from the client or from Safaricom, and it turns the P1 race from "must be prevented
by careful code" into "cannot happen".

### 3.4 Two more, found in passing

**There is no withdrawal ceiling.** Deposits are capped at `MAX_DEPOSIT_KES` (150,000 by
default); a withdrawal's only bounds are `> 0` and the balance. B2C has per-transaction and daily
limits of its own (codes `2`, `3`, `4`; the mirror quotes KES 500,000 daily) that would refuse
the request *after* the customer has been debited. A `MaxWithdrawKES` and a daily cap belong in
config before the first real payout, so the refusal happens at validation and not as a refund.

**`Adjust` is the operator's only tool, and it is the wrong one twice over.** The deferred list
already records the Adjust-then-callback double credit as open by construction
(`auto-bot-deferred.md:30`), and `Adjust`'s dialog now warns against using it for deposits
(`UserDetail.tsx:315-317`). For a stuck withdrawal the same move — refund with `Adjust` — leaves
the withdrawal `pending` and still counted, inserts a `completed` credit, and if a B2C Result
later arrives saying paid, nothing can detect the overlap: `admin_adjustment` rows carry no
reference to the withdrawal. The payout resolve action (§3.2) is the fix, and `Adjust`'s note
should name withdrawals too.

### 3.5 Float — the failure mode deposits cannot have

A payout draws on the business's **Utility** account, and code `1` means it is empty. There is
no synchronous way to check before sending: the Account Balance API is asynchronous like the
rest. But every successful Result reports `B2CUtilityAccountAvailableFunds` — so a gauge fed
from the callback (`mpesa_b2c_utility_available_kes`) costs nothing and gives the alert *"float
below N times the median withdrawal"* before the first customer is refunded for our empty
account. That gauge is the payout analogue of `mpesa_deposits_pending_stale`.

## 4. Gaps and open questions

### 4.1 Safaricom's side — knowable from documentation vs. needs Safaricom

| Question | What the sources say | Tier | Needs Safaricom? |
|---|---|---|---|
| Is B2C enabled on the account? | "B2C requires separate whitelisting and may not be automatically activated during go-live… contact Safaricom's API support" (search summary of community guides); the production checklist says to "select those as well" when applying | community | **yes** |
| Which shortcode can disburse? | "apply for a Bulk Disbursement Account and obtain a B2C Short Code or convert your existing pay bill/till number to one account that can receive and disburse"; the mirror's go-live line: "a shortcode or number that can receive and disburse funds (one account) with Business Admin/Manager operators created" | community + mirror | **yes** — whether `174379`'s production counterpart is that kind of account |
| Where does the initiator come from? | an API user created on the **M-PESA org portal** (not the developer portal), with the "ORG B2C API initiator" role (mirror, code 21's description) | mirror | **yes** — someone with Business Admin on the org portal creates it |
| Which certificate? | sandbox: `keys/sandbox-cert.cer` in Safaricom's node library; production: a different certificate "obtained from Safaricom" | first-party (sandbox) / community (production) | **yes** for production |
| Float | payouts draw on the **Utility** account (mirror; the callback reports its balance); code `1` is *our* insufficient funds | mirror | **yes** — funding it is a finance operation |
| Limits | daily transfer limit and max recipient balance both quoted as KES 500,000 (mirror, codes 4 and 8) | mirror | confirm current figures |
| v3 acceptance | the mirror documents v3; Safaricom's own SDKs send v1 | mirror vs first-party | **confirm in sandbox** with a probe, as `daraja_probe.py` did for STK query |
| Timelines | "2 to 10 business days" for production approval | community | — |

Everything in this table with a "yes" is a conversation, not a code change. **The single biggest
schedule risk in a B2C implementation is not engineering; it is the row "Is B2C enabled on the
account?"** — a build against sandbox that passes every test can still be unusable on the
production shortcode.

### 4.2 The current contract's synchronous assumptions

Everything below assumes a withdrawal is done when the request returns. None of it is true now,
and none of it will be true once a payout is asynchronous — which it will be: initiate →
pending → result, the deposit's shape exactly.

| Where | What it says or does | The problem |
|---|---|---|
| `WithdrawSheet.tsx:176` | **"Arrives in 1 to 5 minutes. No fee."** | a promise nothing in the codebase can keep — the same class of copy the deposit sheet carried until `e627765`, and this one has no reconciler behind it at all |
| `WithdrawSheet.tsx:52-57` | on success: invalidate caches, toast **"It should arrive within a few minutes."**, **close the sheet** | three states (KYC gate, form, confirm) and no fourth: no pending, no result, no polling, no timeout. Compare `DepositSheet`'s six-step machine with its 3s poll and 120s give-up (`DepositSheet.tsx:22, 86-119`) |
| `wallet_handler.go:93` | `202 Accepted` with the raw `models.Transaction` | no payout reference for the customer to quote to support — `Deposit` returns a purpose-built response carrying `checkout_request_id` (`wallet_service.go:132-138`); the payout's `OriginatorConversationID` is the equivalent and should be returned and shown |
| `wallet_service.go:413-417` | socket event `{transaction_id, status: pending, type: withdrawal}` | the only event a withdrawal ever emits; no `account_id` on it, so the client falls back to the active account (`useAccountStream.ts:100-105`) — pre-existing, shared with deposits |
| `HistoryPanel.tsx:130-131`, `TransactionRow.tsx:47, 74-79` | pending **deposits** are pinned to the top and read "Waiting for M-Pesa"; a pending withdrawal sinks into the list with a bare `pending` badge | for ever, today; with a payout it needs the same treatment as a pending deposit, and a failed one needs the B2C reason (§3.1) |
| `admin_queries.go:21-22, 49` → `TodayTotals` (`transaction_repo.go:192-206`) | dashboard tiles `withdrawals_today` / `withdrawals_today_usd` count `status = 'completed'` | **structurally zero** — no withdrawal has ever reached `completed`. A live dashboard figure that is silently wrong |
| `Transactions.tsx:21-23, 30-32, 249` | `isPendingDeposit`, `isStuck`, the "stuck?" marker and the Resolve controls are all `type === 'deposit'` | the console has no view of a stuck payout and no action on one but `Adjust` |
| `transaction_repo.go:144-189` `SearchAll` | searches `reference`, `receipt`, `checkout_request_id`, phone, account, id | a withdrawal has `reference NULL` and neither metadata key; it is findable only by its UUID. The payout's ids and receipt need to be searchable the way `checkout_request_id` became in STK CP0 |
| `routes.go:81-83` | the callback route is public, unauthenticated, unlimited, and binds `mpesaclient.Callback` | a B2C `Result` (`{"Result": …}`) does not decode into it; the payout needs its own two routes, in the same public position, and the same "always answer 200" contract |

The copy question is the one the standard already settled: state exactly what happens, and do
not promise immediacy the server does not offer. Until a payout exists, the honest sheet cannot
say "arrives" at all — which is the argument for §5's first checkpoint.

## 5. Recommended shape for the implementation plan

Not the plan. The shape a plan should take, in the order the STK work proved out, with the
decisions the plan will have to take named so they can be taken deliberately.

### 5.1 A gate before any of it: the Safaricom conversation

Every "yes" in §4.1 is a question only Safaricom can answer, and the answers change the plan:
whether B2C is enabled on the account, which shortcode disburses, who creates the initiator and
with what role, which certificate, how the Utility account is funded. **Start that conversation
before CP1**, in parallel with it, because it is the long pole and nothing in the code shortens
it. A build that passes every sandbox test can still be unusable on the production shortcode.

### 5.2 Checkpoints

**CP0 — make today honest, and close the cheap holes.** No Daraja.
- A `withdrawals_enabled` runtime flag, seeded off, in the `app_settings` pattern the digit and
  bot flags use — because a withdrawal that pays nobody should not be offered, and the KYC gate
  is one admin click from opening it. The sheet says withdrawals are not yet available rather
  than "arrives in 1 to 5 minutes".
- The one-in-flight-withdrawal-per-account partial unique index (§3.3) and the error it maps to.
- `MaxWithdrawKES` and a daily cap (§3.4), validated where deposits validate theirs.
- Decide and document the refund arithmetic (§3.1, option A) and correct
  `balanceAffectingRows`' comment; add the first `assertReconciled` after a non-pending
  withdrawal outcome, even if the outcome is produced by a test double for now.
- Fix `withdrawals_today` or remove it until it can be true.
- The deferred list gains its withdrawal rows.

**CP1 — the client, and the probe.** `pkg/mpesaclient` gains `B2C` (v3, with our id), the
security credential (RSA PKCS#1 v1.5 under a configured certificate, base64 — standard library),
`TransactionStatus`, `AccountBalance`, a `PayoutResult` decoder for `{"Result": …}` and the
timeout payload, and a **B2C allowlist and copy table separate from the STK ones** (§1.4's
same-number-different-meaning table is the argument). `httptest` suite covering every branch, as
CP1 of the STK work did. Alongside it, **`scripts/daraja_b2c_probe.py`**, sandbox-only by
refusal like `daraja_probe.py`, to establish what documentation cannot: whether v3 is accepted;
**what happens when the same `OriginatorConversationID` is sent twice** (the design's spine —
if Safaricom does not dedupe, P1 rests entirely on our guards); the Result and timeout payloads
as actually delivered; the status-by-our-id query. The probe moves real money against a real
account and must never be pointed at production.

**CP2 — the payout service.** A `mpesa_payouts` table (§2.5; never `mpesa_requests`) with our
id unique, Safaricom's `ConversationID`, the full MSISDN, `requested_at`, result code and
receipt, and the reconcile columns 0007 gave deposits. `MpesaPayoutService` as a sibling of
`MpesaService`: one `settlePayout` as the only writer of an outcome, guarded; `OnResult` → a
`WalletService.settlePayout` that is **T→W** — `UpdateStatusIfPending` first, `Wallets.Adjust`
second on failure, nothing on success. `Withdraw` refactored into reserve → request → record
(§2.3), with the request outside every lock and the record through a metadata-only write. Two
new public routes for `ResultURL` and `QueueTimeOutURL`, always answering 200. Mock mode
simulates a Result a few seconds after the request, fails one in N with a B2C code, and has a
stuck fixture like `MockStuckPhone`. Group tests: the P1/P2/P3 races from §2.4 written the way
`TestQueryAndLateCallbackCreditExactlyOnce` was, each with `assertReconciled`; and a mutation
matrix that includes **timeout-treated-as-failure** and **refund-without-the-guard**, with the
now-standard proof that each mutation applied and compiled before its result is read.

**CP3 — the status pass.** A request-then-wait reconciler (§3.2): list pending payouts due a
look, issue a `TransactionStatus` by our id, back off; classification in the status-result
handler. Give-up hands the row to an operator and takes it off the schedule, as CP3 of the STK
work learned to. Metrics `mpesa_payouts_total{outcome}`, `mpesa_payouts_pending_stale`, and the
float gauge from §3.5.

**CP4 — console and UI.** `ResolvePayout` with Mark paid / Mark not paid through `settlePayout`,
audited, the `ResolveDeposit` template. A "stuck?" marker and Resolve controls for withdrawals in
the transactions sheet; `Adjust`'s note extended to name withdrawals; `SearchAll` matching the
payout's ids and receipt. `WithdrawSheet` gains the deposit sheet's state machine — pending with
the payout reference shown, success with the receipt, failure with the B2C reason, timeout with
"we're checking", which will be true — and the `withdrawals_enabled` flag can be turned on. The
first withdrawal e2e spec, and the smoke script's happy path.

### 5.3 Decisions the plan must take, not inherit

1. **v3 or v1.** v3 unless the probe shows the sandbox refuses it. Under v1, §2.3's crash gap is
   unrecoverable by API and the plan must say what an operator does instead.
2. **Refund automatically on explicit failure** (yes — no money moved and most failures are
   ours), **never on ambiguity** (the P3 rule). The plan should write the allowlist of codes that
   trigger a refund and state that everything else waits.
3. **Option A for the refund arithmetic** (§3.1), and the predicate comment corrected.
4. **One pending withdrawal per account**, enforced by the database.
5. **Withdrawals off until the payout exists.** A flag, not copy.
6. **A separate table and a sibling service**, not columns on `mpesa_requests` or parameters on
   `MpesaService`. The reconciler that would otherwise credit a customer for their own
   withdrawal (§2.5) is the reason.

### 5.4 What stays out

The client idempotency key on the money endpoints stays the deferred ticket it already is; the
account-level index makes it a nicety for payouts. Reversal of a completed payout is manual on
the M-PESA portal by Safaricom's own statement, and the plan should say so rather than build
toward an API that does not exist. A withdrawals queue screen in the console is a P3.5-style
item after the marker and the resolve action exist.
